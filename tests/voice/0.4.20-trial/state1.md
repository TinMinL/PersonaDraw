本小姐会先选 **SQLite**，前提是你们做的是有增删改查、筛选或统计的课程项目；如果只是把一份固定数据读出来展示，**JSON 就够了**。先容我抬一句杠：三个人开发，不等于三个人同时写数据库。你们已经排除了后者，就不必替尚未出现的并发问题修宫殿。

不到一万条、单机演示，这两个条件本身不足以决定胜负。真正要看的是：**程序怎样使用数据，以及你们愿意自己维护多少正确性。**

| 你们实际要做的事 | 我会选哪边 | 理由 |
|---|---|---|
| 固定题库、配置、演示素材，主要整份读取 | JSON | 结构直观，容易查看和修改，也方便放进 Git 比较文本差异 |
| 用户、课程、选课等多类数据有关联 | SQLite | 可以用表、查询和约束表达关系，少写一些手工查找与校验 |
| 经常新增、修改、删除，按条件筛选或统计 | SQLite | SQL 和事务能直接承担这些工作，不必自己维护整份文件的读写流程 |
| 纯浏览器静态页面，无后端或现成数据库方案 | JSON 优先 | 接入 SQLite 可能额外涉及 WebAssembly 和持久化配置，未必值得为演示增加工期 |

我偏向 SQLite，首先因为它**不需要另装一个数据库服务器**，由程序通过库访问本地数据库文件，适合你们的一台电脑演示。请别把“用了数据库”自动理解成“要部署一套服务”，SQLite 没有这么大的排场。

再看修改数据。假设一次选课既要新增记录，又要更新名额，SQLite 可以把这几步放进同一事务，成功一起提交，失败一起撤销。JSON 当然也能实现可靠保存，但你们得自己考虑临时文件、替换时机、失败恢复和多步更新的一致性。**数据少，只会减少数据量，不会自动取消写到一半失败这件事。**（演示现场通常不负责体谅程序。）

不过，我也不会给 SQLite 签一张无条件保票。你们需要学一点 SQL、设计表结构；主键、唯一约束等要主动定义，外键检查也要按所用连接配置确认启用。事务只能保住你实际放进去的操作，业务规则仍得由你们写对。它同一时刻只有一个写事务，这对你们目前的条件通常不是障碍；以后若变成多台电脑通过网络共享数据库文件、频繁并发写入，就得重新评估架构。

JSON 的优势我认：如果只读数据、结构简单，直接加载再在内存里筛选，往往已经够用。别为了显得专业，把两天课程作业办成数据库迁移典礼。但若你们已经要自己写关联检查、唯一性判断和可靠保存，所谓“JSON 更简单”，恐怕只是把复杂度从工具搬进了自己的代码。

落地时我会这样安排：**业务数据用 SQLite，固定配置和导入样例用 JSON**；三个人各用自己的本地数据库，通过 Git 共享建表脚本、初始化数据和代码，别合并三份 `.db` 二进制文件。演示前准备一键初始化或重置数据的入口。

所以，按一般管理类课程项目来判断，我推荐 SQLite；若你们确认整个流程就是“加载固定数据 → 展示”，我就改投 JSON。这个例外我认得很爽快，省下来的工期比选型仪式有用。
