本小姐推荐 **SQLite**。先核对一个容易误判的前提：三人开发，就需要远程数据库吗？你们并不同时写同一个库，只在单机演示，两周内也不部署服务器；那么多人协作主要该靠代码、表结构和测试数据的版本管理解决。数据不足一万条，三种方案通常都装得下，真正要比的是查询需求、可靠性和开发负担。

| 方案 | 能得到什么 | 要承担什么 | 对你们的适配 |
|---|---|---|---|
| 本地 JSON | 易读易改，无数据库服务 | 校验、关联、检索和安全写入需自己处理 | 适合结构简单、少量改动的列表或配置 |
| SQLite | 单文件、SQL、事务、索引和约束，无独立服务 | 要设计表、学习基础 SQL、管理结构变更 | 最适合当前课程项目 |
| 远程数据库 | 多端共享，通常有更完善的并发与权限能力 | 服务配置、账号、网络、备份及潜在费用 | 当前收益不足以抵消额外工作 |

JSON 的简单，我认；但别把“能保存”当成“好维护”。常见做法会读入整份数据，修改后重写文件；筛选、分页、跨记录关联都得由你们实现。保存中断还可能损坏文件，需要临时文件替换和备份。若项目只是单一列表、极少更新，它仍是合理选择；一旦有用户、课程、选课关系，本小姐就不愿让你们亲手补一套数据库功能了。

SQLite 的代价也不能藏起来：三个人得约定字段、主键和迁移方式，外键约束要按连接明确启用。它通常同一时刻只有一个写事务，但你们没有同时写库的需求，这个限制暂时并不构成障碍。它把关联查询、唯一性和整批更新交给数据库，两周工期里，这份省心比省掉几句 SQL 更实在。

再看远程数据库，请先说清它解决了哪个现有问题。若以后要多台设备共享数据，它值得重新评估；眼下却会让演示依赖网络与服务状态。托管服务可以省去自建服务器，但账号、权限和连接配置仍要处理，也可能收费。选它当然能练部署，只是那得是课程目标，不能冒充你们已经需要的功能。

实施时，我会这样安排：

1. 第一天定实体、字段、主键和查询清单；把存储操作集中在一个模块，别让界面到处直接读写文件或执行 SQL。
2. 第二至三天建立 SQLite 表、必要约束和常用查询索引；使用参数化 SQL，关联的多次修改放进同一事务。先跑通一条完整业务流程，再铺其他功能。
3. 三人各用本地库；Git 提交建表、迁移脚本与固定种子数据，忽略运行中的数据库文件。结构变更统一编号，避免靠互传数据库碰运气。
4. 第一周完成增删改查，第二周联调与演示；准备初始化、重置和备份恢复说明，关闭程序后再复制数据库文件。

验收也别只看界面能打开。换一个干净目录，按说明初始化，确认数据可重建；逐项检查新增、修改、删除、查询及重启后的持久化。重复主键、非法关联应被拒绝，多步操作中途失败应整体回滚。再导入一万条代表性数据，核对筛选、排序和分页结果，并记录演示机上的耗时。最后断网完整演示一次、从备份恢复一次；这些都过关，本小姐才肯给“可交付”盖章。
